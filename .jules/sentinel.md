## 2025-02-27 - DOM-based XSS via Unescaped Backend Fields
**Vulnerability:** XSS via unmodified fields sent from the backend logic in dashboard.ts. The fields `v.passed` and `v.total` in `verifierStat()`, and `trial.status` in `updateHeader()`, were directly interpolated into HTML without escaping. Additionally, the existing `escapeHtml` implementation would fail to escape (and could potentially crash the UI) if called with non-string arguments because it implicitly expected strings.
**Learning:** Even fields that logically shouldn't contain XSS payloads (such as integers representing passing checks) can be hijacked if the underlying files driving those values are manipulated by a malicious agent outputting string payloads (since the Go backend parses test reports dynamically into maps without strict type guarantees). Trusting external data without UI-side escaping is an XSS vector.
**Prevention:** Ensure that UI templates explicitly HTML-escape all dynamic data, even those thought to be enums or numbers. Make `escapeHtml` resilient to any type (e.g. `null` or `number`) by casting dynamically.
